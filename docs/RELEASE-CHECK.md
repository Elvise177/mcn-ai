### 2.3 更名连带影响面

**先纠正一处事实**：`productName` **并没有**改成 SamePage。

```
electron-builder.yml:2      productName: mcn-ai        ← 未改
desktop/package.json name   mcn-ai-desktop             ← 未改
src/main/index.ts:28        title: 'SamePage'          ← 只有界面字符串改了
```

这是 HANDOFF §4-27 拍板过的：更名只改"看得见的"。**但那条决策记的触发条件正是「买到 Apple Developer ID、做签名与公证的那一单」——也就是你现在这一单。**

#### 实测：改 `productName` 到底会连带什么

§4-27 给的理由是「改 `productName` 会让 `app.getPath('userData')` 跟着变 → 所有已装机器强制重新登录」。**这条理由对本仓库不成立**。

**直接证据**（新脚本 `e2e/probe-name.mjs`，跑在**打包形态**的 app 上，读的是主进程里的真实值）：

```json
{
  "形态": "打包",
  "app.getName()": "mcn-ai-desktop",
  "默认 userData（= appData/getName）": "/Users/…/Library/Application Support/mcn-ai-desktop",
  "Keychain 服务名（推导）": "mcn-ai-desktop Safe Storage",
  "safeStorage 可用": true
}
```

与磁盘上的实际情况逐项对得上：

| 观测项 | 实际值 | 跟谁走 |
|---|---|---|
| `app.asar` 内 `package.json` 的 `name` | `mcn-ai-desktop` | — |
| `app.asar` 内 `package.json` 的 `productName` | **无此字段** | — |
| `Info.plist` 的 `CFBundleName` | `mcn-ai` | electron-builder 的 `productName` |
| 实际 userData 目录 | `~/Library/Application Support/**mcn-ai-desktop**` | **package.json `name`** |
| 实际 Keychain 条目 | `**mcn-ai-desktop** Safe Storage` | **package.json `name`** |

两个"会丢数据"的东西（userData 目录、Keychain 服务名）跟的都是 **package.json 的 `name`**，不是 electron-builder 的 `productName`——因为打包进 asar 的 `package.json` 里**根本没有 `productName` 字段**，`app.getName()` 于是落到 `name` 上。

**结论**：
- 只改 `electron-builder.yml` 的 `productName` → 改变 .app 包名、dmg 名、Finder/Dock 显示名、`CFBundleName`；**userData 与 Keychain 不动，老用户不会被强制重登**
- 真正会导致强制重登的是改 `package.json` 的 `name`，或给 `package.json` 加 `productName` 字段——**这两件事不要做**

#### 当前的名字一致性

| 出现位置 | 现在显示 | 证据 |
|---|---|---|
| 界面（侧栏字标 / 登录页 / 窗口标题 / 菜单项文案 / 诊断报告） | **SamePage** | 走查旧名扫描五个页面各扫一次，零命中 |
| Finder / 应用程序文件夹 / Dock | **mcn-ai** | `lsappinfo` 实测 `LSDisplayName="mcn-ai"` |
| dmg 文件名 | **mcn-ai-0.1.0-arm64.dmg** | 本轮 `npm run dist` 产出 |
| macOS 菜单栏最左那个应用名 | 由 `CFBundleName` 决定 = **mcn-ai** | 同 `LSDisplayName`；**这一条我没能亲眼截到**（读菜单栏要辅助功能授权，本机未授权），按 Electron 的既有行为推的，**发版前请人工瞄一眼** |

客户装完之后，Dock 上是 `mcn-ai`、点开界面写 SamePage。**这是发客户前最好一起收掉的不一致**，而且按上面的实测，收掉它的代价比 §4-27 记的小得多。

#### 裁决（2026-08-19，用户拍板）

**`productName` 不改**，维持内部名，显示层 SamePage 已足够。
dmg 文件名 / .app 包名 / Finder·Dock 名 / 菜单栏应用名**暂时继续是 `mcn-ai`**，
这条不一致**记账不阻断发布**，已写进 HANDOFF §4-27。
**真正的内部改名等"天然要求重登"的时机搭车**——当前最可能的是网关切换那一单。

> 记这条的理由：上面那张实测表说明"改它其实很便宜"，很容易在将来某一轮被人当成
> 顺手改掉的小事。**它便宜不等于现在该改**——第一个正式签名版上少一个变量是更值钱的。

### 🟠 R-05 离线条不会自己下去

`probeCloud()` 只在两处被调用：应用启动（`did-finish-load` 之后）、登录成功之后。**没有周期性重探。**

所以「早上没网开的应用，中午网回来了」这个形态下，那条写着「云端离线…AI 检索已降级为本地全文」的条子**不会自己消失**——只有等到某次真实云端请求成功（问一次库、入一次库、同步队列到期重试）才会被 `markCloudReachable()` 顺手清掉。用户如果只是在知识库里看笔记，那条过期信息会一直挂着。

修法很小：`probeCloud` 在 `reachable === false` 时挂一个 60s 的重探定时器，探通即清、探通即停。

### 🟠 R-09 生成产物那一轮，摘要说「未找到相关资料」

**现场**：截图 `64b-新装-产物已入库`。第二轮问「把刚才那两句话做成 Word」，
折叠摘要写的是「**核对完成，未找到相关资料 · 用时 4.2s**」，而右边产物面板里
就是刚生成的 `新装验收.docx`，正文也写着「已生成 Word 文档」。

**根因**（`renderer/src/lib/step-stream.ts:290`）：

```ts
export function summaryText(steps, elapsedMs) {
  const n = resourceCount(steps)
  return n > 0 ? `检索了 ${n} 份资料 · 用时 ${secs}` : `核对完成，未找到相关资料 · 用时 ${secs}`
}
```

只有两个分支。而 `resourceCount()` **按设计不把产物步骤算成"资料"**（注释里明写着
「生成产物、写文件这类动作不是"资料"，不计」——这条本身是对的）。两条对的规则撞在一起，
结果就是：**只要这一轮没检索到东西、却生成了产物，摘要一定说"未找到相关资料"**。

**为什么值得修**：这是"追问式产物请求"的常见形状（先问一轮、再让它做成文档），
不是边角。而且它正好踩在 §2-19 规则 10b 立的那条规矩上——
**界面上两处对同一件事的说法不许打架**，用户会怀疑那份文档是编的。

**建议修法**（小、收敛）：`summaryText` 增加产物分支——
这一轮有 `render_pptx`/`render_document` 步骤时说「生成了 Word 文档 · 用时 Xs」
（有检索就并列成「检索了 N 份资料 · 生成了文档」）；
「未找到相关资料」只留给**纯检索/扫描且 0 命中**的轮次。

### R-2 建卡器旧卡探测（升级库不再双卡）

**实现**（`src/main/vault/entity-cards.ts`）：建卡前扫全库建一张「已有卡」索引
（判据紧：`entity_kind` 命中，或 `doc_type` 等于该类的 docType；名字过与 `ekey` 同一套的归一）。
同名实体在**任意目录**已有卡 → **跳过新建**，改在旧卡上补关联段；**不自动合并**。

**顺序上「标准位置优先」是刻意的**：已按新版建过卡的库行为一个字不变，
否则升级到这一版会让所有卡当场换家。两边都有的库只打 warn、不擅自处置。

**一处我往前推了半步，得说清楚**：只补关联段的话有个你不会想要的连带——
图谱的 `kindOf()` **只认 `entity_kind`**，而被复用的老页大多只有 `doc_type: 达人档案`，
于是 **135 个达人会从陶土色掉回灰色 doc**，上一轮刚调好的角色配色在升级库上等于白做
（走查还查不出来，因为「五种角色都存在」仍然满足）。
所以复用时**只往老页 frontmatter 补 `entity_kind` / `entity_name` 两个字段**——
纯新增，已有字段一个不改不删。这不是合并（没把两页内容并起来），是给一张本来就是
实体页的文件补两个身份字段，可一眼看出、可手工删。

**真实升级库实测**（拿走查库的 md 骨架、删掉 `30_实体/` 还原成"A-3 建卡器还没跑过"的形态）：

| 角色 | 升级前（原库） | 修复后 |
|---|---|---|
| 达人 | 169 | **169**（没退化） |
| 合作方 | 2 | 2 |
| 枢纽 | 7 | 7 |
| doc | 384 | **247** |
| 文件总数 | 562 | 425 |
| **同名实体卡重复** | 霞飞等 **137 对** | **无** |

`doc` 占比 68.3% → 58.1%，仍满足走查那条「多数安静」的硬约束（≥50%）。

> **顺带查实一条**：这个库里重复的不止霞飞——`30_实体/达人` 169 张与
> `20_公司管理/25_达人档案` 158 张里约 **135 对是同一个人**。霞飞只是最显眼的那个。

**走查现场逮到的第二处（我引入的，已修）**：旧卡探测第一版是**单开一遍全库扫描**，
于是每轮 pipeline 把全库 md 读了**两遍**。走查在「投递箱进度条」那步当场红了
——42 秒的等待窗口被压过去，报「没出现进度条」。**同 HANDOFF 记过的那条教训**：
「pipeline 变慢会把一批当时刚好够用的等待上限逐个变成假红」。
修法是把两次扫描合并进 `collect()` 的同一遍，**不是放宽走查的等待上限**——
慢下来是真的，掩盖它才是错的。

**断言**：`npm run smoke:cards` 新增 12 条（零 token），覆盖 跳过新建 / 旧卡补关联段 /
