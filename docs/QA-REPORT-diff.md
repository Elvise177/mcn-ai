## 9. 附录：本次跑批撞到的问题

按严重度排。都**没有改任何产品代码**，只记录。

### A-1 【高】整包拖入递归 0 文件，静默返回 n=0

`InboxOrchestrator.enqueue`（`desktop/src/main/inbox/orchestrator.ts:317`）对目录只 `readdir` 一层取文件，**不递归**。
Maggie 源数据顶两层全是目录，所以真·新客户把 `maggie-personal-data` 整个文件夹拖进窗口 →
**copy 0 个文件，`enqueue` 返回 0，界面什么都不会发生**（不报错、不提示、不出进度条）。

- 为什么严重：这是新客户批量导入的**第一个动作**，而静默 n=0 是最伤的失败形态——用户会以为软件坏了或者自己拖错了，没有任何线索
- 本次绕过方式：按 26 个叶子目录逐个 `enqueue(files, subdir=<相对路径>)`，等价于用户把每个叶子文件夹分别拖进去
- 顺带：`enqueue` 拿到 0 个文件时也不该静默——`doEnqueue` 只在 `paths.length` 非空时才调，但「目录里一个文件都没捞到」这条路径上没有任何反馈

### A-2 【高】`03b_tag_rules.py` 不在 `cli.py` 链上 → 40% 的笔记零 frontmatter

`09_pii_guard` 会把含 PII 或纯表格的文件登记进 checkpoint，让 `03_tag_llm` 跳过它们（正确，敏感数据不出网）。
但旧版随后跑 `03b_tag_rules.py` 给这批文件做**零模型的规则打标**兜底，而桌面版 `cli.py` **完全没有引用 03b**：

```
cli.py 的链: 02_convert → 09_pii_guard → 03_tag_llm → 07_sensitive_enrich → 04_gen_moc
缺的:                                  ↑ 这里旧版还有 03b_tag_rules
```

结果：**37 篇（40%）在新版里一行 frontmatter 都没有**——无 `doc_type`/`category`/`sub_category`/`tags`/`summary`。
命中的正是最需要被检索到的一批：全部 20 份人力绩效档案、人才盘点总表、职级体系、财务收支利润表、人效核算、达人信息表、两份年框合作表、三份年度目标管理总表。

- 连带影响 1：这 37 篇进不了 `_主题索引`（按 AI 标签分组），MOC 里也没有摘要行
- 连带影响 2：`07_sensitive_enrich` 想给数据表补「结构摘要」时调 `fm_replace`，而它的实现是 `text.replace("---\n", …)`——**没有 frontmatter 就静默无操作**，摘要写不进去（已核对：正文里没有被错注入，属于静默丢弃而非污染）
- 连带影响 3：阶段二问库时，「谁的绩效最好」「今年利润多少」这类问题命中的文档没有任何结构化元信息

**修复原则（2026-08-17 拍板，与 A-8 合并为一个修复大单）**：`03b_tag_rules` 接回链，敏感文件默认走它——
标签与结构化摘要**必须有，且零外发**。见 A-8 的三态选项。

### A-3 【中】双链从 352 条掉到 2 条——实体页前置依赖不存在

`07_sensitive_enrich` 的建链靠三张实体清单：`20_公司管理/25_达人档案/*.md`、`40_带货/产品/*.md`、`30_课程/课程计划/*.md`。
模板新建库里前者是空目录、后两者**目录都不存在**（`DEFAULT_LAYOUT` 里根本没这两条），所以实体扫描必然扫出 0 条。
而达人卡本该由 `08_table_to_cards.py` 产出——那个阶段不在链上（A-2 的同类问题）。

于是形成级联：`08` 不在链上 → 达人档案空 → `07` 建链 0 条 → 库里只剩 MOC 那种目录型链接。
新库唯一活下来的 2 条双链来自 `07` 的合作方页（从文件名挖出的「向日花」「霞飞」），那条路径不依赖实体清单。

### A-4 【中】转换失败与格式不支持在界面上完全不可见

本轮 6 个文件没有产出笔记（4 个 PDF 转换失败 + `.xmind`/`.doc` 格式不支持），但：

- 六阶段进度条**全绿**，任务终态 `succeeded`，标题「投递箱处理完成」
- 失败清单只写进 `80_资料库/convert_fail.log`，界面不读、不提示
- 格式不支持的那 2 个连 `convert_fail.log` 都不进，纯静默
- 98 个原件全部被归档进 `00_投递箱/.done/20260817/`，包括没转换成功的那 6 个——用户看投递箱空了，会认为全部入库了

### A-8 【高】`09_pii_guard` 只挡 LLM 打标，不挡上云

`09_pii_guard` 的设计前提是「PII 绝不出网」，它拦住了 `03_tag_llm`。但 `cloudSync` 对本轮变更的 md **一律 `ingestNote`**，
没有任何敏感标记检查（`desktop/src/main/inbox/orchestrator.ts:372` 那个循环里只有 50 篇上限，没有 guard 判断）。
也就是说**登录状态下，那 37 篇被判定为敏感、刻意不给模型看的文件，照样会被切片+嵌入推到 Supabase 私人层**——
包括 20 份员工绩效档案、财务收支利润表、达人信息表。

- 本轮**未实际触发**（隔离实例未登录），是准备阶段二、决定问库走哪条检索路径时读代码发现的
- 这已经不是新旧版回归问题，而是产品的安全边界与用户预期不一致：
  守卫的名字与注释都在说「零出网」，实际只覆盖了两条出网路径里的一条

**修复原则（2026-08-17 拍板，与 A-2 合并为一个修复大单）**：

1. **敏感标记笔记不进 `cloudSync`**（不上云驻留）；本地全文检索与问答引用照常可用
2. **`03b_tag_rules` 接回链**（= A-2 的修法），敏感文件默认走规则打标——标签与结构化摘要必须有，零外发
3. **设置页「知识入库」组加三态选项**：敏感资料 `仅本地规则打标`（默认）／`允许 AI 打标`（明示会发送给模型）／`与普通文件相同`（含云端同步）
4. **文案原则**：对用户说清真实边界——「敏感文件不离开你的电脑，AI 回答时仍可引用」

> 这四条是修复大单的输入，不在本次对比的改动范围内（本次零产品代码改动）。

### A-7 【中】批量导入的上云只推前 50 篇，剩下的静默丢弃

`InboxOrchestrator.cloudSync`（`desktop/src/main/inbox/orchestrator.ts:372`）是 `for (const rel of changed.slice(0, 50))`。
本轮 92 篇（本来会是 95 个 md 变更），登录状态下**只有前 50 篇会进云端私人层，另外 42 篇永远不上云**，
而阶段完成消息只说「N 篇上云」——不说被截断了多少。

- 这条本轮**没有实际触发**（隔离实例未登录，`cloud_sync` 走的是 `skipped: 未登录`），是准备阶段二时读代码发现的
- 影响面：新客户装机第一次批量导入通常就是几十上百篇，而「问库带引用」在登录状态下走的是云端语义检索——
  没上云的那些在对话里等于不存在，但界面上它们在库里、在图谱里、看得见摸得着
- 50 这个上限本身可能是为了控住单轮时长与 embedding 成本，但**截断必须说出来**（哪怕只是「另有 42 篇待同步」）

`04_gen_moc` 生成的每个 `_MOC_*.md` 都写「归属：`[[Library_MOC]]`」，但它自己不生成这个文件，模板新建库也没有。
