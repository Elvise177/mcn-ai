## 0. 五条硬发现（会改方案，不是风险提示）

### 0-1 打标 checkpoint 会把实体抽取整个吞掉——「缓存命中大半」与「全库有实体」不可兼得

`03_tag_llm.py:98-109`：`done` 集合只按 **path** 判重，命中即**整篇跳过**，不进 LLM。
checkpoint（`80_资料库/.checkpoint.jsonl`）里**没有任何版本/schema 字段**。后果是二选一：

| 跑法 | 缓存 | 实体产出 |
|---|---|---|
| 在已跑过的库上重跑（如 `/tmp/mcnai-qa-vault`） | 55/55 命中 | **0 个实体**——一篇都不会重新打标 |
| 在全新库重跑 | 0 命中 | 全量，但 55 次调用全额付费 |

**验收要求里那句「打标缓存应命中大半」在这一单里不成立**，必须当成一次全量重打标来报预算。
修法：checkpoint 记录加 `rev`（prompt/schema 版本号），`done` 判定改成 `path + rev` 都相同；
无 `rev` 的旧记录视为 `rev=0` → 本次必然全量重跑一次，此后只有再改 schema 才会再全量。

（评估过"只补实体的短 prompt"第二条链路：输出能省 ~75%，但输入仍要送正文 6000 字符，
合计只省约 25%，换来两套 prompt 两处维护。**不推荐**，直接 rev 全量重跑。）

实测：`desktop/resources/pipeline/_internal/` 里有 `pptx`、`PIL`、`lxml`、`pymupdf`、`python_calamine`，
**没有 `xlsxwriter`**；而 `~/Documents/AI/pkb-pipeline/.venv/` 里它是装着的（3.2.9）。

### 0-3 `cloudSync` 的敏感判定读内存索引，新建卡有竞态窗口 → 敏感继承卡可能上云

`inbox/orchestrator.ts:488` 的 `isSensitive` 走 `vaultManager.noteAt(rel)?.frontmatter?.sensitive`，
而 `noteAt` 只是内存 Map（`vault/index.ts:113`），由 chokidar 填充，`awaitWriteFinish` **800ms**。

`cloudSync` 在 pipeline 子进程 `close` 之后**立刻**跑。现在这条路能成，是因为敏感标记由
`09_pii_guard` 在链路**很靠前**写下，到收尾时早就进索引了。
**建卡器是链路尾部的新阶段**，它写的卡离 `close` 只有几十毫秒 → `noteAt` 极可能返回
`undefined` → `isSensitive` 判 false → **敏感继承卡被推上云**。这正好打穿 A-8 刚修好的边界。

修法（二选一，推荐前者）：`cloudSync` 对 `changed` 逐条**从磁盘读 frontmatter**判敏感，不依赖内存索引；
或建卡器把"敏感卡清单"随 stage 事件回传，主进程直接用。

### 0-4 图片引用在渲染层是死链（三重原因，缺一不可修）

笔记正文写 `![](_assets/xxx/1.png)` 之后：

1. `Markdown.tsx` 用 marked 出 `<img src="_assets/…">`，**相对路径会按渲染进程文档 URL 解析**
   （dev 是 `http://localhost`，prod 是 `file://…/out/renderer/index.html`），不是 vault 路径 → 404
2. 改写成 `file:///…` 也不行：`PURIFY_CFG.ALLOWED_URI_REGEXP`（`Markdown.tsx:8`）只放行
   `https?|mailto|wiki`，`file:` 会被 DOMPurify **剥掉**
3. 就算放行，dev 形态下 `http://` 页面加载 `file://` 资源会被 webSecurity 拦（关 webSecurity 不可接受）

唯一干净解：主进程 `protocol.handle('mcnai-asset', …)` 注册自定义协议（限定只能读当前 vault 根之下），
渲染前把图片 src 重写成 `mcnai-asset://…`，并把该 scheme 加进 `ALLOWED_URI_REGEXP`。
两处（笔记预览、聊天气泡）共用 `FastMarkdown`，改一处两处都好。

## 1. 五个必答问题

### 1.1 实体抽取加进 03，对打标成本与缓存命中的影响

**成本（prompt 变长这部分，可忽略）**
基线（QA §0，Maggie 全量）：55 次调用 / 输入 141,260 / 输出 46,795 / 内置口径 ¥0.66。
加三个实体数组后：system prompt +约 200 token/文件（+7.8% 输入）、输出 +约 60 token/文件（+7% 输出）
→ **合计 +8%，¥0.66 → ¥0.71**。真实账单口径按 DeepSeek 分时计价最坏 ×2（HANDOFF §3-9），
**按 ¥1.5 报预算**。

**缓存（这才是真成本）**：见 0-1。这一单必然吃一次全量重打标，之后靠 `rev` 恢复正常命中。
**结论：本单验收那一轮的打标成本 = 一次全量 ≈ ¥1.5，不是增量。**

**敏感那 37 篇**（内容不出门，规则级识别）——实测老库口径 31/95 篇按文件名可判敏感，
规则源三条，全部零模型：
- 文件名 `…x{品牌}年框|合作` → partner（`07` 已有的正则，直接复用）
- 表头字段（`table_summary()` 已经在提字段名）含「姓名/账号昵称/达人」列 → 该列**列值**即 talent 候选
  （口径沿用 `08_table_to_cards.py` 的 `SAFE_FIELDS` 白名单，身份证/银行卡/手机号绝不进）
- 文件名里的专名（品牌 × 产品词）→ product 候选

**一个必须先说清的后果**（实测，见 §1.3 表）：达人实体的**主要来源就是敏感表**。
所以"敏感继承"条款会大面积生效——大部分达人卡会是 sensitive 卡（不上云、规则打标）。
这不是 bug，是设计的必然结果，但它直接影响验收标准的读法，见 §5-1。

### 1.2 建卡器的插入点，与对 a1-enqueue 断言的影响

### 1.3 归一策略的具体规则

原则用户已定：**宁可两张卡，不可错合**。所以下面是「四道规则 + 一道 LLM 仲裁 + 一道兜底」，
LLM 只在**规则判不明**时介入，且它只有"合并/不合并/不确定"三种回答，**不确定一律不合并**。

老库里真实存在的形态（实测样例，说明规则不是拍脑袋的）：

| 形态 | 实例 |
|---|---|
| 带备注括号 | `小熊饼干（日常版）`、`七阿七（带货版）`、`长卿子（带货版` |
| 带真名备注 | `灰太太(孙芳兵)`（需求里点名的那条） |
| 尾部分号拼接 | `霞飞双层高光粉；定轴半年抛` vs `霞飞双层高光粉` |
| 尾部标点噪声 | `蜡笔小欣.`、`LuLu.` |

**R1 字面归一（无损，必合）**：Unicode NFKC → 全角转半角 → 去首尾空白与尾部 `.。,，、；;` →
中英文之间空格压缩。`蜡笔小欣.` = `蜡笔小欣`。

**R2 备注剥离（必合，但两个名字都记）**：剥掉尾部成对括号 `()（）[]【】` 及其内容 →
得到 `base`。`灰太太(孙芳兵)` → base `灰太太`。**卡名用 base，括号里的内容进
`aliases` 字段**（真名属 PII 时不进卡正文，只做匹配用，见 R6）。

**R3 前缀包含（只在有强证据时合）**：A 是 B 的前缀且 `len(A) >= 3`，
且 B 去掉 A 之后的剩余部分以分隔符（`；;/、·-（(`）开头 → 合并到 A。
`霞飞双层高光粉；定轴半年抛` → `霞飞双层高光粉`。
**`len(A) >= 3` 是硬阈值**：两字前缀会把「霞飞」把「霞飞双层高光粉」吃掉，那是错合。

**R4 类型隔离（禁止跨类合并）**：talent / product / partner 三类各自归一，**永不跨类合并**。
「霞飞」是 partner、「霞飞双层高光粉」是 product，规则上根本不该相遇。

**R5 LLM 仲裁（只跑候选对，且只在 llm_ready 时）**：规则跑完后，对**同类、同首字、编辑距离 ≤2 或
互为子串**但没被 R1–R3 判定的候选对，批量送一次 flash（一次调用判全部对，返回
`[{a,b,verdict:"same|different|unsure"}]`）。**只有 `same` 才合并**；`unsure` 与失败一律不合并。
候选对量级：老库 179 张卡实测候选 <30 对 → **一次调用，≈¥0.01**。
`--skip-llm` 时这一步整个跳过（所以 a1-enqueue 零影响）。

**R6 落盘形态**：卡 frontmatter 记 `entity_name`（归一后）、`aliases: [...]`（所有被合并进来的写法）、
`merged_from: [...]`（审计用）。**归一是幂等的**：重复入库时先按 `entity_name` 命中，
命中不了再按 `aliases` 命中，都不中才建新卡。

**冲突与增量**：卡里区分「自动区」与「用户区」——自动区用锚注释包起来
（`<!-- mcnai:auto:start -->` … `<!-- mcnai:auto:end -->`），重复入库**只重写自动区**。
另存 `auto_hash`：若自动区当前内容与 `auto_hash` 不符 = 用户手工编辑过 → **不覆盖**，
把新内容写进 `## ⚠️ 待合并（自动生成，与你的编辑有冲突）` 区段并在 stage 事件里报数，
面板给一句「N 张卡因你手工编辑过而未覆盖」。这与 M-27 那条「冲突保用户版」是同一条原则。

**敏感继承**：卡记 `sources_sensitive` / `sources_normal` 两个来源列表。
`sources_normal` 为空 → 卡写 `sensitive: true`（不上云、走规则打标）；
非空 → 普通卡，**且正文自动区只允许写来自 `sources_normal` 的内容与双链**，
敏感来源只留一条不带字段值的链接。
⚠️ 这条直接推翻 `08_table_to_cards.py` 现有行为——它把签约信息（合作类型/等级/分值）
整块同步进卡，而那些字段全部来自敏感表。**新规则下这段只能进 sensitive 卡。**

**概念关联字段位**：卡模板留 `related_concepts: []` 并注释 `# 06_concepts 接链后填充（本单不做）`。

## 5. 验收标准与断言（断言到参数层）

### 5-1 ⚠️ 「达人卡与老库 08 同数量级」这条要先改口径

实测（拿旧库 156 张达人卡逐张回扫 95 篇库内笔记）：

| 门槛 | 达人卡 | 产品卡 |
|---|---|---|
| 老库实际产出（08 表格拆卡） | **156** | 13 |
| 被 **≥2 篇任意文档**提及 | 140 | 5 |
| 被 **≥2 篇非敏感文档**提及 | **9** | 3 |

**所以：只靠「≥2 篇提及」这一条入口，产出是 9 张，与老库差两个数量级。**
差在哪：老库那 156 张来自**达人信息表一行一卡**，不是"被两篇文档提到"。
而达人信息表正是那 37 篇敏感文件之一。

**建议（待拍板 §6-1）**：建卡器保留**两条入口**——
(a) 提及派生（entities ≥2 篇）→ 有语境的卡；
(b) 宽表拆卡（继承 `08` 的 `SAFE_FIELDS` 白名单口径，达人信息表/签约表一行一卡）→ 名册型卡。
两条入口合流后走同一套归一。**结果形态**：约 9 张普通卡（有非敏感文档支撑）+ 约 130+ 张
**sensitive 卡（不上云、规则打标、卡内不含敏感字段值）**。数量级对得上老库，敏感边界也守得住。

### 5-2 对照指标（Maggie 全量重跑）

| 指标 | 基线 | 目标 |
|---|---|---|
| 双链总数 | 旧 352 / 新 2 | 回到 **300+**（口径：`vault/reader.ts` 的**正文内**唯一链接，与 QA §1.2 同一套） |
| 三类卡数量 | 达人 156 / 产品 13 / 合作方 2 | 同数量级；**合作方必须含霞飞、向日花** |
| 图谱横向关联 | 子树边 147 | 明显上升，且**卡节点非孤点** |

### 5-3 断言清单（参数层，不接受弱断言）

- **实体抽取**：随机抽 5 篇 AI 打标笔记，frontmatter 三个数组必须存在；至少一篇的
  `entities_talent` 能在正文里 `grep` 到该名字（**抽出来的东西必须在文里真出现过**）
- **归一**：构造 `灰太太` / `灰太太(孙芳兵)` / `灰太太 ` 三种写法 → **有且只有一张卡**，
  `aliases` 含另两种；构造 `霞飞` 与 `霞飞双层高光粉` → **两张卡，且不同类**（R4 反例）
- **不错合反例**：构造 `小飞蛾` 与 `小飞象` → 两张卡（编辑距离 1 但 LLM 判 different / unsure 都不许合）
- **增量与冲突**：同一批重复入库两次 → 卡数不变、`updated` 而非重建；
  手工改过自动区的卡 → 第二次入库**内容不被覆盖**且 stage 事件报出「N 张未覆盖」
- **敏感继承**：仅由敏感文档支撑的卡 `sensitive: true`；`cloudSync` 的 `held` 计数必须**包含**这些卡
  （这条要用**新建卡**验，不能只用 09 早就标好的老文件——0-3 那个竞态只在新文件上出现）
- **敏感卡内容**：普通卡（如灰太太）正文里**不许出现**来自敏感表的字段值（签约日期/合作类型/等级/分值），
  正则扫一遍
- **a1-enqueue 新增**：卡目录下所有 stem ∩ 源文件 stem = ∅
- **抽图**：含图 docx / pptx / pdf 各一份入库后 → `_assets/{笔记名}/` 下文件数 == frontmatter `images` 计数；
  正文里的 md 图片引用**逐条能解析到磁盘上真实存在的文件**；渲染层截图里 `<img>` 的
  `naturalWidth > 0`（**量像素，不数标签**——用量页那 14 根柱子的教训）
- **附件**：拖一张图进输入框 → 缩略图出现 → 发送 → 气泡里 `naturalWidth > 0` →
  主进程临时目录里确有拷贝且路径进了 prompt（拿 `window.__steps` 那套原始事件比对）
- **chart**：产出的 pptx 用 python-pptx 反读，断言 `slide.shapes` 里**真有 chart 类型的 shape**
  且 series 数据与 outline 一致（不接受"文件生成了"这种弱断言）
- **步骤流**：附件与图片相关的新文案进 `smoke:steps`，仍守「一个英文工具名都不许漏」

## 6. 需要拍板的四件事（其余我按上面的默认值做）

**6-1 达人卡的两条入口要不要都开？**（§5-1）
不开 = 达人卡只有 9 张，验收标准「与老库同数量级」达不成；
开 = 数量级对上，但会多出 130+ 张 sensitive 卡（不上云、图谱上只与敏感文档相连）。
**我的建议：开，这是唯一能同时满足"数量级"和"敏感不出门"的形态。**

**6-2 `layout.json` 加 `products` / `partners` 两个键？**（§0-5）
不加就只能让建卡器往 07 写死的 `40_带货/产品`、`30_课程/课程计划` 里写——
那两个路径与向导建的库结构对不上，用户在文件树里会看到两个凭空冒出来的目录。
**我的建议：加，并让 07 与建卡器都读 layout（读不到回落写死值，保老库回归）。**

**6-3 图片要不要降采样？**（§1.4）
不降：+473MB（vault 从约 600MB 涨到约 1.1GB），"原图"名副其实；
降（长边 >1600px 或 >800KB 时压到 1600 / q85）+ 每篇上限 50 张：+约 60MB，肉眼几乎无差，
但严格说不再是"原图"（原件本身仍在库里，随时可打开）。
**我的建议：降 + 上限 50，并在笔记 frontmatter 记 `images_original_bytes` 留痕。**

**6-4 打标 checkpoint 加 `rev` 全量重跑一次，确认？**（§0-1）
这是本单打标预算的全部来源（≈¥1.5）。不加 rev 就得手删 checkpoint——
那样每次改 prompt 都要人工记得删，迟早漏。
