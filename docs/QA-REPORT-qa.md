## 4. 根因：`search_knowledge` 对「整句话」查询必然返回空

### 4.1 现象

13 轮里标准档有 **7 轮**是「三次检索全空 → 回答『知识库里没有』」，而那些资料**确实在库里**。

### 4.2 机制

`src/main/vault/search-worker.ts` 的检索器：中文按 **unigram + bigram** 切词（`tokenize`），
MiniSearch 配的是 **`combineWith: 'AND'`**。两者叠加的效果是——
**查询串里每一个字、以及每一对相邻字，都必须在同一篇笔记里出现，缺一个就整条查询归零**。

空格分开的关键词能活下来；黏成一句自然语言的查询几乎必死，因为它带进来一堆**跨词边界的二元组**
（「公司年度目标」里的「司年」、「星母第二期」里的「母第」），这些组合在任何一篇笔记里都不存在。

### 4.3 决定性对照（只差一个空格）

| 查询 | 命中 | 同样的词加空格 | 命中 | 缺的是什么 |

| `2026年上半年收支` | **0** | `2026 上半年 收支` | **0** | 缺「年上」「半年」「年收」 |

### 5-A 标准档不会绕路，增强档会——这是本轮两档差距的主要来源

Agent SDK 除了 `search_knowledge`，还给了模型 `Bash` / `Grep` / `Read` / `Glob`（能直接扫 vault 目录）。

|---|---|---|
| 检索全空后的行为 | 再试 2 次同类查询 → 放弃 → 回答「库里没有」 | 转用 `Bash`/`Read` 直接扫文件 → 找到并作答 |

**所以两档的差距，本轮主要不是「推理能力」的差距，而是「会不会绕过坏掉的工具」的差距。**
检索修好之后这个对比要重跑才有意义——现在的数据不能用来论证「增强档值不值这个价」。

### 5-B 标准档实际走的是 inferera，不是出厂的 DeepSeek 官方

`ai.tiers()` 实测：标准档 `baseUrl` = `https://api.inferera.com`，`overridden: true`。
原因是隔离实例的 config 是我为了做真实打标手工预置的（有 key、有 vaultPath），
`migrateTiers` 据此判定为**老用户**，把「升级前生效的线路」原样搬成了标准档映射（设计 §4-23 的老用户分支）。

- **模型串没有被换掉**：`deepseek-v4-pro` / `deepseek-v4-flash` 原样，用量记录里 `degraded: false`，
  实际服务模型 = `deepseek-v4-pro`，与期望一致 —— 按 §4-17 的实测表，inferera 对这两个名字是原样服务
- **这是环境造成的，不是产品缺陷**：真实新装机首启时 config 是空的，会走出厂映射
- 但它说明一件事：**「老用户」的判据是「配过库或落过任意一把 key」**，而首次登录 provision 就会落 key。
  出厂映射到底在多少台真实新机上生效过，值得单独查一次

### 5-G 用量页会把这一轮显示成 ¥154，实际账单约 ¥50

`src/main/usage/index.ts` 的 `INPUT_KEYS` 正则把 `cache_read_input_tokens` 与 `cache_creation_input_tokens`
一起并进 `input`，然后按**基础 input 单价**计费；`scripts/usage-report.mjs` 用同一套口径。
但这两类 token 的真实价格完全不同——缓存读约为基础价的 **10%**，缓存写约 **125%**。

- 总输入 2,947,550 token 里，**2,529,309 是缓存读**（占 86%）
- 产品口径 ¥153.83 ／ 缓存折价口径 ¥49.79 —— **高估约 3.1 倍**

  几乎整笔账都是按全价计的缓存读

这不影响对话功能，但用量页的定位是**成本透明化**（设计 §4-25 / C′ 人民币化那一单的核心）。
老板看到一个系统性偏高 3 倍的数字，要么吓得不敢用增强档，要么发现对不上账之后不再信这个页面。

> 口径本身是可以讨论的（保守估计也是一种选择），但**现在页面上没有任何地方说明它是保守口径**，
> 脚注只写了「费用为估算值，以实际账单为准」——那句话解释不了 3 倍的系统性偏差。

### 8.2 兜底双指标（2026-08-18 改口径）

原来那个「走到 Grep 兜底的题数」把三件不同的事算成一件，判别力为零。拆成两个：

| 指标 | 定义 | 验收 | 修前 | 第 0 批 | **第 1 批** |
|---|---|---|---|---|---|
| **绕过检索型异常** | 该检索却 0 次调用 | =0 | 0 | 1 | **1 → 0**（见 §8.4） |
| **检索失败型兜底** | 调用了检索但无结果，转扫描 | =0 | 7（7 题三次检索全空） | 0 | **0** |

**「检索失败型兜底」这一列目前是人工判读的**：批跑脚本只记了工具**名**没记工具**返回值**，
机器分不出「检索空了才扫」和「检索命中后为了枚举再扫」。判读依据是工具序列——
第 1 批里凡是调过检索的题，下一步都是 `Read`（读命中的那篇），没有一题是检索完立刻转 `Grep` 换路子。
**下一轮批跑应当把工具返回值也记下来**，这个指标就能机器判了，成本几乎为零。
