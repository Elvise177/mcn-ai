# 检索优化第二单方案：实体卡 → wiki 页（引擎层）

> 状态：**待批**（2026-09-05 出方案，批后动工）
> 依据：`docs/RETRIEVAL-BENCH.md` §5——策略层第一单跑完，跨文档全命中卡在 40%、M-S5 仍 0 命中，剩下的缺口全在引擎层。
> 原则：不改尺子来迎合实现；每一条改动都对着基线里具体哪几题的失败说话，改完跑 bench 对照。

## 0. 三种失败形状（本轮 bench 现场）

| 形状 | 现场 | 根因 |
|---|---|---|
| A. 泛标题、正文无词 | 《总结.md》（M-K1 / M-X1 / M-X4）：标题两个字，正文写的是"第一期 / 班委 / 第四组"，从头到尾没有"星母计划"四个字；任何含"星母"的检索都不命中，模型只能靠《数据版》答 | 索引只吃 **title / body / tags** 三个字段；这篇笔记的身份信息全在**目录路径**（`…/星母培训计划/数据复盘/总结.md`）和它被谁链接上，而这两样都不在索引里 |
| B. AND 匹配失败 | 《金字塔达人孵化方案》对「孵化 培训 项目」：三个词得**同时**出现在同一篇，它没有"项目"；J-X2 的《编制模型》正文没有"年度目标" | 检索器第一遍是全 AND，空了才退到模糊 OR；而模糊那遍会把它标成"相近结果"、排在真命中后面，加上覆盖率闸门 0.6，多一个不相关的词就整篇落空 |
| C. 排名靠后 | 《2026年中复盘会议纪要》对「中台 复盘」排第 15（J-X1）、对「编制 人力」排第 19（J-X5）；《人力编制测算模型》基线里排在两份绩效档案后面 | MiniSearch 的 BM25 里长文档（xlsx 转出来的大表，几万字）靠词频压过短文档；title boost 3 不够抵消。放宽到 10 条也够不着 15、19 位 |
| D.（留给 embedding）词汇鸿沟 | 《社群VIP》对「潜水 / 不动手 / 发出第一条视频」（M-S5 三轮检索 0 命中）；基线里《公域营销行动指南》对「找博主 签约」、《管理者的素养》对「带团队 修炼」 | 问题与文档没有任何共同词，标题 / 路径 / 标签 / 摘要都没有——关键词系统的天花板 |

## 1. 方案：wiki 摘要区

### 1.1 它是什么

把现有**实体卡**（`vault/entity-cards.ts`，A-3 建的达人 / 产品 / 合作方卡，自动区里已有「相关文档」清单）推广成 **wiki 页**：每个实体、每个主题各一页，自动区里放一段**可检索的摘要区**——

```
<!-- mcnai:auto:start -->
## 摘要区
星母培训计划 · 主题页 · 关联 14 篇
- [[…/数据复盘/总结|总结]] — 第一期星母培训计划复盘，筛选14人，发现积分机制漏洞（复盘 · 2025-06）
- [[…/数据复盘/第一期星母计划线上复盘数据版本|第一期数据版复盘]] — 星母计划第一期线上数据复盘，分析课程、作业、班委及机制问题
- [[…/方案流程设计/第二期星母计划线上·完整培训方案|第二期完整方案]] — 15天线上培训方案，通过复制迭代和创新作业筛选潜力达人
…
关键词：星母计划 星母培训计划 第一期 第二期 班委 积分 入选 复盘
<!-- mcnai:auto:end -->
```

每一行 = 一篇关联文档的**标题 + frontmatter `summary` + 类型/日期**，末尾一行「关键词」= 这一页所有关联文档 tags 的并集。**不调 LLM**：摘要是 `03_tag_llm` / `03b` 已经写好的 `summary`，标签是已有的 `tags`，全是复用。

主题页从哪来：① 实体（已有三类）；② **目录主题**——资料库下二级/三级目录名（`星母培训计划`、`半年度复盘/2026`、`年框`）各一页，这是 A 形状的钥匙；③ **标签主题**——出现 ≥3 篇的 tag（`阿米巴`、`年框`、`人效`）各一页。落位 `30_实体/` 旁边新开 `30_实体/主题/`（layout.json 加一项，老库默认值），敏感文档只列链接不带摘要（沿用 `04_gen_moc` 的 R-03 规矩），wiki 页本身按"任一关联文档敏感 → 页敏感"继承（同实体卡）。

### 1.2 三种形状各怎么解

**A. 泛标题正文无词 → 两手**

- 索引加 **`path` 字段**（目录段，不含文件名），boost 2：`总结.md` 的 path 含"星母培训计划 / 数据复盘"，查「星母计划」立刻命中——这是纯引擎改动，零 LLM、零新文件，`search-worker.ts` 加一个字段十行代码
- wiki 主题页《星母培训计划》摘要区里那一行「总结 — 第一期星母培训计划复盘，筛选14人…」本身就含"星母"，模型读主题页时看到它带 summary 的链接，会去 Read。**主题页是第二保险**，也顺手解决"模型只读到 1-2 篇就作答"里"不知道还有哪几篇"的那一半
- 预期：M-K1 / M-X1 / M-X4 的《总结》从"任何检索不命中"变成命中，跨文档全命中里这三题的缺口补上

**B. AND 匹配失败 → 放松一档 + 主题页天然全词**

- 检索器加一档 **"n−1 AND"**：全 AND 空了、先试"去掉任意一个词"的 AND（词数 ≥3 时），仍空才退模糊 OR。「孵化 培训 项目」去掉"项目"→《金字塔方案》《三层漏斗》都命中，且**不标相近**（三个词里两个是真命中）。同样 `search-worker.ts`，二十行
- 主题页《达人孵化》（由 tag `达人孵化` 聚出来，≥3 篇）一页里同时含"孵化 / 培训 / 项目 / 金字塔 / 三层漏斗 / 100天"，全 AND 直接命中主题页 → 模型顺着链接读三篇
- 预期：M-X3 补上《金字塔》；J-X2 的《编制模型》靠 tag 主题页《年度目标》带出来（它的 summary 含"营业收入 / 编制"，与"年度目标"仍不重合，**这题只能靠主题页把它列在《目标管理》目录主题下**，是本方案里最没底的一条，先按"部分解决"记）

**C. 排名靠后 → 提标题、压长表、主题页置顶**

- `title` boost 3 → 6，新 `path` 字段 boost 2；BM25 的 `b` 从默认 0.7 调到 0.3（削弱长度归一化里长文档的词频优势——大表几万字靶不到问题时不该靠"提到很多次"赢）。这两个参数要用 bench 的 45 题**逐题回归**，不是拍脑袋定：目标是《会议纪要》进前 10、绩效档案不再压过《编制模型》，同时关键词题 95% 召回不掉
- wiki 页排名：主题页标题就是主题名、正文全是关键词密集的摘要行，天然排最前；模型先读主题页再按链接读文档，等于**用主题页替代了"翻到第 15 位"**
- 预期：J-X1 / J-X5 的《会议纪要》进前 10；跨文档全命中目标 40% → ≥70%（10 题里 M-X1 / M-X3 / M-X4 / J-X1 / J-X5 五题各补一份；J-X2 存疑）

### 1.3 解不了、留给本地 embedding 的

D 形状三题（M-S5《社群VIP》、以及基线时期的 J-S2 / J-S4）问题与文档零共词，摘要区也帮不上（《社群VIP》的 summary 是"美妆带货社群VIP课程包培训方案"，没有"潜水 / 发视频"）。这一类只有语义匹配能救。建议**第三单**再做，且只对**摘要区**做 embedding：

- 语料 = wiki 页的摘要行（几百到一两千条短句），不是全文切片——体积小两个量级，本地跑得动、也不用碰云端那条有 file_path 问题的链路（HANDOFF §3-13）
- 模型候选：本地 `bge-small-zh` / `text2vec-base-chinese`（ONNX，~100MB，CPU 单条 <50ms），或复用云端 `text-embedding-3-small`（成本敏感，每次全库刷一遍约 ¥0.1，可接受但要上云、敏感页得排除）
- 接法：`search_knowledge` 全 AND 与 n−1 AND 都空时，拿 embedding 在摘要行里找 top-5，**标成"语义相近"**返回（与现在的模糊回退同一档位，走同一套"先验证再引"规矩）
- 第三单再评估，本单不做——先看 A/B/C 三手把关键词能吃的都吃干净，剩下多少题真需要 embedding，数字说话

## 2. 落点与工作量

| 项 | 落点 | 量 |
|---|---|---|
| `path` 字段 + boost/b 参数 | `vault/search-worker.ts`、`searcher.ts`（docs 结构加 path） | 小；参数用 bench 逐题回归定 |
| n−1 AND 档 | `vault/search-worker.ts` `runSearch` | 小；`smoke-vault` 加断言（「孵化 培训 项目」命中金字塔且不标相近；「完美日记」仍 0） |
| wiki 主题页生成器 | `vault/entity-cards.ts` 旁新 `vault/wiki-pages.ts`：目录主题 + 标签主题 → 自动区摘要区；实体卡的自动区也补摘要行 | 中；复用实体卡的自动区 / 冲突 / 敏感继承机制 |
| 触发 | 与建卡同一时机（入库 run-end 之后），增量：只重写关联集合变了的页 | 小 |
| 配置 | `layout.json` 加 `topics` 目录（默认 `30_实体/主题`），走 `readVaultConfig` 默认值 | 小 |
| 验收 | `smoke:cards` 加 wiki 页断言（敏感继承、自动区不碰用户手写、摘要行数）；`smoke-vault` 加检索断言；bench 全量一轮对照第一单（≈¥14） | — |

**不做的**：不改题、不改判分；不用 LLM 生成摘要（有现成的）；不碰云端语义检索；不改 `SEARCH_SHOWN_LIMIT`（10 保持，看主题页能不能让"前 10"够用）。

## 3. 风险

- **主题页数量**：Jerry 库目录主题 ~40、标签主题（≥3 篇）~60，加实体卡共约 250 页，检索时主题页会经常排第一——这正是想要的，但模型可能**只读主题页不读原文**就作答。对策：主题页摘要区末尾写一句「以上为摘要，回答前请 Read 原文」，并在 bench 里看"读到率"有没有掉
- **参数回归互相拉扯**：提 title、压 `b` 可能让关键词题的某几题掉名次。所以参数不拍脑袋，跑 bench 45 题逐题看，任何一类召回下降就回退那一档
- **旧库升级**：老库没有 `topics` 目录、`layout.json` 没那一项 → 默认值兜底，同实体卡 0.2.0 升级的路
- **成本**：本单零 LLM 调用；验收一轮 bench ≈ ¥14（含判分）
